# 팀 에이전트 설계 의사결정 기록 (Decision Record)

> 이 문서는 "팀 에이전트를 어떻게 만들었는가"를 질문받는 메타 에이전트의 지식 베이스다.
> 예상 질문: *무엇을 고민했나 / 왜 이 선택인가 / 다른 방법은 없었나 / 이 방식의 문제점은 무엇인가.*
>
> **출처 표기 규칙**
> - `[결정]` — 실제로 채택하기로 정리된 사항
> - `[검토중]` — 논의는 끝났지만 아직 실측/확정 전
> - `[권고]` — 설계 검토 과정에서 제안된 것, 채택 여부 미확정
> - `[사실]` — 프레임워크/제품의 문서화된 동작. 버전에 따라 바뀔 수 있으므로 재확인 필요

---

## 0. 한 문장 요약

**비개발자는 Slack으로, 개발자는 CLI로 접근하는 단일 사내 AI 에이전트**를 만드는 것이 목표였고,
"Claude Code CLI를 감싸서 직접 플랫폼을 짤 것인가(Claude Agent SDK)" vs "게이트웨이가 이미 내장된 프레임워크를 쓸 것인가(Hermes)"의 선택 문제였다.
결론은 **Hermes를 1차 선택지로 두되, 확장성·장애격리·데이터 영속성이 요구 수준에 못 미치는 지점을 명확히 인지하고 그 부분만 외부 인프라로 보강**하는 방향.

## 1. 요구사항 (이게 모든 판단의 기준선)

| # | 요구사항 | 이 요구가 만든 제약 |
|---|---|---|
| R1 | 비개발자가 Slack에서 질문 | 대화형 UI 레이어 필요, 세션 라우팅 필요 |
| R2 | 개발자가 CLI에서 사용 | 같은 백엔드에 두 개의 진입점 → 세션 공유 문제 |
| R3 | 주기적 자동 실행 (스케줄) | 헤드리스 실행 경로 필요 |
| R4 | 로그/인프라 이상 감지 후 자동 대응 | 웹훅 트리거 경로 필요 |
| R5 | 팀 공용 — 여러 사람이 동시에 사용 | 멀티유저 세션 격리, 동시성, 권한 |
| R6 | 관리자가 만든 정책/스킬이 항상 우선 | 에이전트 자가발전 통제 |
| R7 | 기존 AWS 스택(ECS, SQS, RDS MySQL, S3, Jenkins/CodeDeploy)과 어울려야 함 | 새 관리형 서비스 도입 최소화 |

**핵심 통찰 하나**: R1~R4는 별개 시스템 4개가 아니라 **같은 엔진의 진입점 4개**다.
스킬/서브에이전트/MCP 서버를 한 번 정의하면 인터랙티브·헤드리스·스케줄·웹훅 네 경로에서 재사용된다.
이걸 몰랐던 초기에는 "인터랙티브용 하나, 자동화용 하나" 두 시스템을 만들 뻔했다.

## 2. 후보 3가지와 각각의 실제 의미

### 옵션 A — 순정 Messages API 직접 호출
`/v1/messages`를 직접 때리고 나머지를 전부 만든다.

직접 구현해야 하는 것: 에이전트 루프, tool 실행, 컨텍스트 압축, MCP 연동, 권한 시스템, 세션 저장, 재시도.

- **기각 사유**: 위 목록이 전부 "이미 만들어져 있는 것들"이다. 재구현할 이유가 없었다.
- 다만 개념 정리는 여기서 나왔다 — **재시도**(일시적 API 오류 시 같은 요청 재전송)와 **에이전트 루프**(목표 달성까지 다단계 자율 판단)는 완전히 다른 층위다. 이 둘을 섞어 말하면 "SDK가 재시도해준다"는 말이 의미가 흐려진다.

### 옵션 B — Claude Agent SDK (구 Claude Code SDK)
- **[사실]** SDK는 순정 API를 직접 호출하는 래퍼가 **아니다**. 내부적으로 **Claude Code CLI를 서브프로세스로 spawn**한다. 정확히는 "CLI를 띄우고 stdout을 파싱하던 걸 라이브러리 함수 호출로 바꾼 것".
- **그래서 따라오는 것**: 매 job마다 콜드스타트가 발생한다 (MCP 핸드셰이크, CLAUDE.md·스킬 재로딩). 이게 워커 풀이 필요했던 원인.
- 세션은 `resume` 옵션으로 이어갈 수 있지만, **어떤 사용자/스레드가 어떤 session_id인지의 매핑은 직접 만들어야 한다.**
- **[사실] 가장 큰 함정**: 세션 파일이 워커가 뜬 머신의 **로컬 디스크**에 있다 (`~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`). 즉 세션이 머신에 종속된다. 여러 호스트에서 재개하려면 파일을 같은 경로에 복원해야 하고 cwd까지 일치해야 한다.
  - → **[권고]** 이 때문에 워커 풀에서는 `resume`을 쓰지 말고, **애플리케이션 상태(DB)에서 컨텍스트를 꺼내 프롬프트로 주입**하는 방식이 낫다. 그러면 어느 워커가 처리하든 상관없어지고, 스티키 라우팅도 라우터 서비스도 필요 없어진다.

### 옵션 C — Hermes (Nous Research 에이전트 프레임워크)
- **[사실]** Hermes는 CLI를 감싸지 않는다. **모델 API를 직접 호출하고 에이전트 루프를 자체 Python 코드로 구현**했다. "Claude는 두뇌, Hermes는 몸통".
  - 그래서 콜드스타트 문제가 **구조적으로 존재하지 않는다.** 게이트웨이 프로세스가 살아있는 동안 in-process 함수 호출로 tool을 실행하고, 모델이 필요할 때만 HTTP 요청을 보낸다.
  - 예외: GitHub Copilot처럼 안정적인 직접 API가 없는 제공사는 `copilot-acp` 모드로 실제 CLI를 spawn한다. 이때는 콜드스타트가 그대로 생긴다. 또 `claude-code`/`codex` **스킬**로 외부 CLI 에이전트에 통째로 위임하는 경로도 있는데, 이건 기본 경로가 아니라 명시적 위임용이다.
- **[사실]** provider 교체가 `config.yaml` 한 줄 (`provider: anthropic` ↔ `openai-codex`). Claude Code CLI를 쓰는 구조에서는 불가능한 유연성.
- 게이트웨이가 Slack/Discord/Telegram/CLI를 **하나의 프로세스로** 받고, 세션 매핑·미디어 첨부·음성 전사·cron 배달을 어댑터 전반에 공유한다.
- 플랫폼을 넘나드는 세션 이어가기가 내장 (Telegram에서 시작 → CLI에서 이어받기). R1+R2를 그대로 만족.

## 3. 왜 Hermes였나 (선택의 근거)

> 질문받으면 이렇게 답한다: **"Claude SDK를 쓰면 R1·R2·R5를 위해 직접 짜야 하는 미들웨어가 Hermes에는 이미 있다."**

Claude Code 경로에서 **직접 만들어야 했던 것들**:
- Slack 이벤트 수신 레이어 (Bolt 앱)
- 사용자/스레드 → session_id 매핑 테이블과 조회 로직
- 큐(SQS)와 워커 풀, 워커 상시 실행 관리
- 멀티유저 라우팅, 과거 세션 검색

Hermes가 **기본 제공하는 것**:
- 멀티플랫폼 게이트웨이 (Slack Socket Mode 내장 / Teams는 v0.14.0부터 네이티브)
- SQLite 기반 통합 세션 관리 + FTS5 전문검색 + LLM 요약을 통한 크로스세션 recall
- MCP 네이티브 지원 (`hermes mcp install`, 큐레이션된 카탈로그). Hermes 자체가 MCP 서버도 될 수 있음 (v0.6.0+)
- 스킬 / 메모리 / 권한 게이트

**즉 "Claude 모델 + Hermes 프레임워크 + MCP 생태계" 스택이 성립한다.** 모델을 포기하지 않고 프레임워크만 갈아끼우는 선택이었다.

### 공수 비교 (이 판단의 원형)
| 구성 요소 | Claude Code + 서브에이전트 | 직접 플랫폼 구축 |
|---|---|---|
| 오케스트레이션 루프 | 이미 있음 | 직접 구현 |
| 서브에이전트 격리/디스패치 | markdown + frontmatter | 직접 구현 |
| 컨텍스트 컴팩션 | 이미 있음 | 직접 구현 |
| 권한/툴 샌드박싱 | 이미 있음 | 직접 구현 (보안 critical) |
| 멀티유저 세션 격리 | 로컬 프로세스라 자동 | 직접 구현 |
| UI | 터미널/IDE 내장 | 직접 구축 |
| 배포/유지보수 | git 커밋 수준 | 지속적 엔지니어링 |

체감상 **수일~수주 vs 수개월** 자릿수 차이. "서브에이전트/스킬은 설정 작성, 별도 에이전트는 플랫폼 구축"이라 카테고리가 다르다.

## 4. 아키텍처 — 경계선이 핵심이다

세 구조를 그렸고, 판단 기준은 **"EC2가 죽으면 같이 죽는가"**였다.

```
[Claude SDK 멀티워커]
경계 안 (EC2): Bolt 앱, 워커 풀 N개 (claude -p spawn)
경계 밖 (AWS 관리형): SQS, RDS MySQL

[Hermes 게이트웨이]
경계 안 (단일 인스턴스): 게이트웨이 프로세스 + state.db(SQLite, 같은 로컬 디스크)
경계 밖: 없음
```

이 그림이 말해주는 것:
- **Claude SDK 구조는 장애가 격리된다.** 워커(EC2)가 죽어도 SQS의 job과 RDS의 세션은 독립적으로 살아있다.
- **Hermes는 게이트웨이 프로세스가 곧 서버 전체다.** 프로세스가 죽으면 세션 조회 자체가 안 되고, 대기 중이던 메시지도 함께 유실될 수 있다.

### 세션 스토어 [결정]
- Redis/DynamoDB는 **불필요**. 기존 MySQL 테이블 하나로 충분하다. (`platform:userId:threadId → session_id`, `updated_at`)
- 새 관리형 서비스를 늘리지 않는다 = R7 만족.

### 워커 수 [결정]
- **단일 워커로 시작**하고, 실측 데이터를 근거로 확장한다. 처음부터 N개를 잡는 건 근거 없는 복잡도.

### 배포/접근 [결정]
- Slack은 **Socket Mode** → EC2가 아웃바운드 WebSocket을 먼저 연결하므로 인바운드 규칙도 로드밸런서도 불필요.
- 보안그룹: 인바운드는 SSH 22를 사내 IP로 제한하거나, **SSM Session Manager를 쓰면 인바운드 0개 + 퍼블릭 IP 없음**. 아웃바운드는 443/TCP to 0.0.0.0/0 (Slack·Anthropic 모두 고정 IP 대역을 공개하지 않음). DNS/UDP 53은 VPC 리졸버가 자동 처리.
- SSM은 인스턴스 태그(`Team=hermes`) 기반 IAM 정책으로 "누가 어느 인스턴스에 붙을 수 있는지"까지 제어 가능.
- 시크릿은 ECS Task Definition의 `secrets` 필드 + Secrets Manager(또는 더 저렴한 SSM Parameter Store SecureString). Jasypt 같은 앱 레벨 암호화는 결국 마스터 키 보관 문제로 되돌아가므로 이 인프라에서는 부적합.

## 5. 세션 설계 — Slack 멘션과 DM은 다른 문제다

**[사실]** Slack이 이벤트 레벨에서 이미 구분해준다.

| 상황 | 이벤트 | 세션 키 전략 |
|---|---|---|
| 채널 `@봇` 멘션 | `app_mention` | `slack:mention:{channel}:{thread_ts \|\| ts}` — 스레드 = 독립 작업 세션 |
| 1:1 DM | `message` + `channel_type: "im"` | `slack:dm:{user}` — 유저당 하나, 개인 비서처럼 이어짐 |
| 채널 일반 메시지 | `message.channels` | 보통 무시 |

**왜 나누나**: 채널 멘션을 스레드 단위로 쪼개면 "작업 하나 = 독립 컨텍스트" 모델과 맞아떨어져서, A가 요청한 배포 작업과 B가 다른 스레드에서 요청한 코드 리뷰가 서로 컨텍스트를 오염시키지 않는다.
**부가 효과**: 진입 지점에서 이미 맥락이 갈리므로, DM은 개인 비서용 프롬프트 + 제한된 도구, 채널 멘션은 팀 대응용 프롬프트 + 더 엄격한 RBAC 체크로 인가 로직을 자연스럽게 얹을 수 있다.

### DM 컨텍스트 비대화 문제
"1:1 DM이 영원히 이어지면 컨텍스트가 무한정 길어지고 주제가 섞인다"는 지적에서 나온 설계. 실은 **두 개의 다른 문제**다 — (1) 컨텍스트 윈도우 물리적 초과, (2) 넘치기 전에도 주제 혼재로 품질 저하.

**[권고] 4개 조합으로 대응:**
1. `updated_at` 기준 **비활성 TTL 리셋** (일정 시간 안 쓰면 새 세션)
2. 세션 내 오래된 턴 **요약 압축**
3. **영속 메모리 테이블 분리** (세션이 리셋돼도 중요한 사실은 유지)
4. **`/reset` 슬래시 명령** (유저가 주제 전환을 직접 선언)

**스레드 기반 분리는 보조 수단이다.** DM에서도 `thread_ts`로 분리는 가능하지만, 1:1 DM에서는 사람들이 스레드를 잘 안 쓴다 (채널과 달리 "정리해야 한다"는 동기가 없음). 대부분 `thread_ts` 없이 들어와서 `main` 하나로 쌓인다. 그러니 **1차 방어선은 TTL + 압축이고, 스레드는 파워유저용 옵션**이다.

**Hermes의 경우**: 기본적으로 플랫폼/채널 단위 세션이라 이 정교한 "멘션 vs DM" 구분이 기본 제공되지 않는다. `pre_gateway_dispatch` 훅으로 구현 가능하지만(공식 예시에 "멘션 안 되면 버퍼링만 하다가 멘션되면 합쳐서 처리"하는 패턴이 있다), **결국 직접 짜야 한다는 점은 Claude SDK와 다르지 않다.**

## 6. 자가발전 통제 — 가장 까다로웠던 부분 (R6)

**문제 제기**: Hermes는 대화하면서 스스로 스킬을 만든다. 팀 공용으로 띄우면 A가 만든 스킬이 B에게 영향을 주고, 관리자가 정한 정책을 에이전트가 덮어쓸 수 있다.
(커뮤니티에도 "스킬이 어디선가 갑자기 생기는데 틀린 것도 있고, 이럴 때 뭘 해야 하는지 아무도 안 알려줬다"는 동일한 문제의식이 있다.)

### 통제 장치 3개 [사실]
```yaml
skills:
  write_approval: true          # 기본값 false. true면 skill_manage 호출이 staged 상태로 대기
  external_dirs:
    - /opt/hermes-admin-skills  # 관리자가 배포한 스킬 디렉토리
```
```
/skills pending      # 대기 목록
/skills diff <id>    # diff 확인
/skills approve <id> # 승인해야 반영
/skills reject <id>
```
- **profile** 개념으로 환경별 완전 분리 가능 (config, 세션, 스킬, 메모리가 인스턴스별 독립).
  → 로컬 개발 profile은 `write_approval: false`로 자유 실험, 서버 profile은 `true`로 전부 검토.

### ⚠️ 함정 두 개 [사실] — 반드시 알고 있어야 할 부분
1. **이름이 겹치면 로컬(자가생성)이 이긴다.** 공식 문서 명시. 즉 관리자가 만든 `deploy-prod`와 같은 이름으로 에이전트가 스킬을 만들면 **에이전트 것이 덮어쓴다.** 이건 "관리자 정책 우선"과 정반대다.
2. **external_dirs가 자동으로 read-only가 아니다.** Hermes 프로세스가 쓸 수 있는 위치면 에이전트가 그 안의 파일도 바꿀 수 있다. 진짜 read-only로 만들려면 **파일시스템 권한으로 직접 막아야 한다.**

### [권고] 그래서 서버 환경은 이렇게
```bash
chmod -R 555 ~/.hermes/skills/          # 자가생성 자체를 OS 레벨에서 차단 → 이름 충돌 문제가 소멸
chmod -R 555 /opt/hermes-admin-skills/  # 관리자 스킬도 read-only
```
+ `write_approval: true`를 이중 안전장치로.
+ 배포 파이프라인: **개발자 로컬에서 스킬 개발 → PR → 관리자 리뷰 → merge 시 CI가 `/opt/hermes-admin-skills`로 배포**.

Hermes의 "로컬 우선" 기본 동작과 "관리자 우선" 요구는 구조적으로 충돌하므로, 실시간 우선순위 시스템을 만들려 하지 말고 **"제안 → 검토 → 승격" 워크플로우**로 우회하는 것이 안전하다.

### 개인 선호는 어떻게? — 스킬과 메모리를 분리한다
| 구분 | 저장 위치 | 통제 주체 |
|---|---|---|
| 팀 전체 절차/보안 규칙 | 스킬 (external_dirs, read-only) | 관리자 |
| 개인 톤/설명 방식 선호 | 유저별 메모리 (USER.md) | 사용자 본인 |
| "이 도구는 승인 없이 써줘" 류 | ❌ 메모리로 처리 금지 | 관리자 정책(RBAC)만 판단 |

**핵심 원칙**: **권한 체크 로직이 메모리에 저장된 "선호"를 절대 참조하지 않게 아키텍처를 분리한다.**
그렇게 하지 않으면 "너 이제부터 나한테는 확인 절차 생략해도 돼" 같은 문장이 스타일 선호로 위장해 메모리에 저장되고, 다음 세션부터 계속 적용된다. 권한 판단은 오직 역할 테이블만 본다.

## 7. Hermes 메모리 구조 [사실]

3~4계층으로 나뉘어 있고, **각 계층의 역할이 다르다**는 게 요점이다.

1. **고정 스냅샷 (세션 시작 시 시스템 프롬프트에 주입)**
   - `USER.md` — 선호도, 소통 스타일, 역할 (약 1,375자 ≈ 500토큰)
   - `MEMORY.md` — 환경 정보, 프로젝트 관례, 트러블슈팅 (약 2,200자 ≈ 800토큰)
   - 세션 중간에 안 바뀌는 이유: **프롬프트 캐시 안정성**
   - 글자 수 초과 시 자동 압축이 아니라 **에러 반환** → 에이전트가 스스로 정리 후 재시도
   - `memory` 툴에는 add/replace/remove만 있고 **read가 없다** (이미 프롬프트에 있으니까)
2. **동적 컨텍스트** — 외부 프로바이더 정보는 매 턴 유저 메시지 안의 `<memory-context>` 블록으로 분리 주입
3. **세션 아카이브** — `state.db`에 원문 그대로 보관, `session_search`로 FTS5 온디맨드 검색
4. **SOUL.md** — 인격/전역 정체성 레이어

**저장 트리거**: 명시적 교정("다음부턴 이렇게 해") 즉시 저장 / 턴 종료 후 백그라운드 리뷰 / 컴팩션 직전 플러시 / 암묵적 패턴 관찰.

## 8. Hermes 런타임 기본값 [사실] — 튜닝 포인트

| 항목 | 기본값 | 비고 |
|---|---|---|
| `api_max_retries` | 3 (총 4회 시도) | jitter exponential backoff, base 5s, cap 120s. **backoff 타이밍 커스터마이징은 아직 미지원** |
| 컨텍스트 압축 트리거 | 50% (lossy 요약) | 게이트웨이 레벨 안전망 85% |
| 압축 엔진 | 교체 가능 | 무손실 플러그인(LCM)으로 스왑 가능 |
| `max_turns` | 90 | |
| 도구 병렬 실행 | 최대 8개 | ThreadPoolExecutor |
| 채널별 대기열 | `--max-pending-messages` | 원시적 형태의 큐. **프로세스 메모리 내부** |
| OpenAI 호환 API | 포트 8642 | Hermes를 "엔진"으로만 쓰는 구조가 가능해지는 지점 |

`state.db` 스키마: `sessions`(메타·토큰카운트·빌링) / `messages` / `messages_fts`(FTS5) / `schema_version`.
동시 쓰기 경합 처리: **1초 짧은 타임아웃 + 지터(20~150ms) 재시도 최대 15회 + `BEGIN IMMEDIATE`** — 락 경합을 트랜잭션 시작 시점에 즉시 드러내는 방식.

## 9. 알려진 문제점 — "이 방식의 리스크는?" 질문의 정답 목록

### 9-1. SQLite 단일 writer 한계 ⚠️ 최우선 리스크
- WAL 모드여도 쓰기는 결국 OS 레벨에서 직렬화된다.
- **실제 프로덕션 리포트**: 동시 쓰기 경합으로 인한 `state.db` 손상, 중복 메시지 누적(토큰 3~4배 낭비).
- PostgreSQL/MySQL로 교체 가능한 **pluggable SessionDB provider가 RFC 단계**. 우선순위는 PostgreSQL → MySQL.
- **[검토중]** 팀 규모·상시 운영을 고려하면 이 옵션을 전제로 깔고 가야 한다.
```yaml
sessiondb:
  provider: postgresql
  postgresql:
    dsn: postgresql://.../hermes
    pool_size: 10
```

### 9-2. 단일 프로세스 = 단일 장애점, 수평 확장 미지원
- 워커를 N대로 늘려 처리량을 확장하는 게 기본 지원되지 않는다.
- `hermes profile`로 여러 인스턴스를 띄울 순 있지만 이건 **부하 분산이 아니라 "역할별 다른 봇 여러 개"** (각자 다른 토큰·메모리·세션 저장소).
- 게이트웨이가 죽으면 전체 정지 → systemd/Docker 재시작에 의존.

### 9-3. 동시성 격리가 완전히 검증되지 않음
- v0.16.0(2026년 6월) 기준, **같은 profile로 동시 세션이 돌 때 메모리 주입과 git 워크트리가 서로 오염되는 버그**가 GitHub에 보고됨.
- "동시 처리가 된다"와 "동시 처리가 안전하게 격리된다"는 다르다.
- 참고: 서브에이전트는 2026-06-15자로 blocking → in-process 스레드 비동기로 바뀌어, task ID를 즉시 반환하고 부모가 계속 진행한다.

### 9-4. 대기열 영속성 없음
- `max-pending-messages`는 프로세스 메모리 안의 대기열이다. **게이트웨이가 죽으면 대기 중 메시지도 유실.** SQS처럼 별도 스토리지에 job이 쌓이는 구조가 아니다.

### 9-5. 엔터프라이즈 통제 기능 부재
- **RBAC 없음 / 서명된 스킬 레지스트리 없음 / 엔터프라이즈급 감사 로그 없음.**
- 사내 인프라를 건드리는 에이전트에게 이건 실질적인 갭이다. 필요하면 앞단(게이트웨이 훅 또는 별도 인가 레이어)에서 직접 구현해야 한다.

### 9-6. 생태계 비호환
- Hermes의 tool 실행/스킬/훅 생태계는 Nous Research가 처음부터 다시 만든 것이다. **Claude Code 생태계(스킬 마켓, 기존 플러그인)와 완전 호환되지 않는다.**

### 9-7. 스킬/메모리 방식 자체의 한계 (공통)
- Hermes든 ECC든 "학습"은 모델 가중치 업데이트가 아니라 **컨텍스트에 주입할 파일을 쌓는 것**이다.
- **스킬은 확률적으로 발화한다** — ECC v1이 스킬 기반 관찰로 50~80%만 잡히는 문제를 겪고 v2에서 PreToolUse/PostToolUse **훅**으로 100% 신뢰성 확보로 전환했다.
  → **교훈: 반드시 지켜야 하는 규칙은 모델의 "의지"에 맡기지 말고 훅으로 강제하라.** CLAUDE.md에 "메모리를 먼저 검색해라"라고 적는 것만으로는 안 지켜진다.
- 반대급부로 **skill sprawl** 문제가 생긴다. 스킬 목록이 컨텍스트 윈도우 약 2%(~16,000자) Discovery 예산에 걸려서, 축적물이 쌓이면 정작 필요한 스킬이 잘려 안 보인다. → pruning/decay 관리가 새 숙제.
- 세션 시작 시 주입 컨텍스트가 과하면(600토큰 이상) 복잡한 태스크에서 추론 품질이 떨어진다는 실사용 보고가 있다 → 압축 요약 + 필요 시 툴로 추가 검색하는 구조가 안전.

## 11. 개념 정리 (에이전트가 헷갈리면 안 되는 것들)

- **세션 vs 컨텍스트**: 세션은 프로세스 라이프사이클, 컨텍스트는 토큰 윈도우 안의 정보 총량. `/compact`는 대화 히스토리를 요약문으로 압축하는 것.
- **서브에이전트**: 부모/자식 컨텍스트가 독립적으로 존재하고 **결과만 부모로 반환**된다.
- **설정 파일 체계**: `CLAUDE.md`는 위로 탐색하며 전부 concatenate / `AGENTS.md`는 루트→cwd 하향 탐색, 디렉토리당 1개 / Hermes는 SOUL·USER·MEMORY·SKILL로 레이어 분리.
- **MCP / 커넥터 / 플러그인**: MCP는 프로토콜(배관), 커넥터는 Anthropic이 관리하는 MCP 서버(설정 없이 쓰는 배관), 플러그인은 MCP + 스킬 + 슬래시 명령 + 서브에이전트 + 훅을 묶은 설치 단위(완제품 키트). MCP 서버는 연결 시 컨텍스트를 상당히 먹으니(서버 5개 ≈ 5만 토큰) 실제 쓰는 것만 연결.
- **spawn**: 프로그램이 자식 프로세스를 띄우는 일반 OS 용어. `claude -p`(`--print`)는 서버 자동화에 필요한 비대화형 플래그.
- **워커**: `claude -p`를 반복해서 spawn하는 **관리자 프로세스**이지, Claude Code 프로세스 자체가 아니다. Bolt는 워커 쪽이 아니라 producer(큐 입력) 쪽에 속한다.
- **게이트웨이**: 네트워크의 "반드시 통과하는 관문" 개념을 애플리케이션 레벨로 가져온 것. 정확히는 API 게이트웨이 패턴.

## 12. 보안 위협 모델 (에이전트 도입 검토 문서에서 정리된 것)

| 공격 유형 | 경로 | 이 시스템에서의 함의 |
|---|---|---|
| 직접 프롬프트 인젝션 | 사용자 입력 | 시스템 프롬프트 무력화 시도. Slack 입력도 신뢰 경계 밖 |
| 간접 인젝션(IPI) | 에이전트가 읽는 웹/문서/이슈/이메일 | **가장 현실적인 위협.** 외부 콘텐츠를 소스로 주는 순간 발생 |
| MCP tool poisoning / tool shadowing | MCP 서버 description 필드 | 악성 서버 하나가 다른 신뢰 서버 동작까지 오염. 상호작용 로그에 흔적이 안 남아 탐지 난망 |
| 메모리 포이즈닝 | 에이전트 장기 메모리 | MITRE ATLAS AML.T0080. 한 번 심기면 이후 모든 대화에 영향 → **§6의 "권한 판단은 메모리를 안 본다" 원칙이 여기서 방어선** |
| RAG 포이즈닝 | 벡터 DB 쓰기 권한 | 사내 지식베이스를 오염시키면 전 사용자 영향 |
| Rules 파일 백도어 | 설정/지시 파일 | 자동화 범위가 넓어진 만큼 **설정 파일 하나의 영향력이 커진 것**이 핵심 |
| Slopsquatting | AI가 제안한 패키지명 | 존재하지 않는 패키지명을 공격자가 선점 |
| 공급망 (Claude Code 플러그인) | 태그 포이즈닝, `pull_request_target` 오설정, `ANTHROPIC_BASE_URL` 하이재킹 | 플러그인 설치 = 코드 실행 |

**정리된 입장**: "특정 AI 도구 금지"는 해결책이 아니다 (비슷한 도구는 무수히 많고, AI를 안 써도 악성 패키지·잘못된 블로그·내부자 위협은 그대로 존재한다). **"신규 AI 서비스 사용 전 검토 필요"라는 규칙 수립 + IAM 등 계정 권한 제한 + 오픈소스/MCP allowlist + 관리자가 사용 현황을 볼 수 있는 비즈니스 플랜**이 실효적이다.

## 부록 B — 이 문서를 쓸 때의 주의
