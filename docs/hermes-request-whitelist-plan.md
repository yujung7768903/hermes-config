# LLM 전달 전 요청 화이트리스트 — 계획

> 작성일: 2026-08-06
> 상태: **구현됨 (2026-08-09) — `plugins/prompt-gate/`, 기본 `mode: observe`**
> 관련 문서: [hermes-security-policy.md](hermes-security-policy.md) 6-1·6-2절

## 1. 문제

현재 보안 계층 L0~L3 은 모두 **모델이 요청을 이미 해석한 뒤** 개입함. 차단 시점이 도구 호출
직전이므로, 요청 자체가 모델에 도달하는 것을 막지 못함.

| 계층 | 개입 시점 | 막는 것 |
| --- | --- | --- |
| L0 platform_toolsets | 세션 생성 | 채널에 없는 도구 노출 (원격 채널엔 실효 없음) |
| L1 approvals.deny | 도구 호출 직전 | 명령 문자열 패턴 |
| L2 security_guard hook | 도구 실행 직전 | 도구 인자 |
| L3 security-filter | 결과 반환 직전 | 결과의 민감 정보 |

따라서 프롬프트 인젝션, 업무 범위 밖 지시, 사회공학 문구는 전부 모델에 그대로 도달함.
차단은 모델이 "도구를 쓰겠다"고 판단한 뒤에만 걸리므로, 모델 판단 자체를 신뢰하는 구조임.

## 2. 확인된 사실

새 개입 지점을 만들 필요 없음. `pre_gateway_dispatch` 훅이 이미 그 자리에 있음.

| 항목 | 확인 내용 | 근거 |
| --- | --- | --- |
| 훅 존재 | `hooks.pre_gateway_dispatch` 등록 가능 | config.yaml `hooks` 절 |
| 훅 등록 절차 | command + script_mtime 승인 필요 | shell-hooks-allowlist.json |

> **[2026-08-09 정정] 이 절의 전제 두 개가 틀렸다.** 코어 소스(v0.18.0)로 확인함.
>
> 1. **셸 훅이 아니라 플러그인 훅이다.** config.yaml `hooks:` 절에 등록은 되지만
>    (`VALID_HOOKS` 에 이름이 있어서), `_parse_response` 가 `pre_tool_call` ·
>    `pre_verify` 외의 이벤트에서는 action 을 해석하지 않고 버린다
>    (agent/shell_hooks.py:602-606). 즉 셸 스크립트가 `{"action":"skip"}` 을 내도
>    무시되고 정상 디스패치된다. 등록은 `ctx.register_hook("pre_gateway_dispatch", cb)`
>    로 하고, **`shell-hooks-allowlist.json` 승인은 필요 없다.** 대신
>    `plugins.enabled` 에 들어가야 한다.
> 2. **메시지 위치는 `event.text` 다** (MessageEvent 객체 속성).
>    `payload["extra"]["event"]["text"]` 가 아니다 — 셸 훅 wire 포맷에서도 그 자리는
>    dict 가 아니라 `json.dumps(default=str)` 로 문자열화된 repr 이라 인덱싱이 안 된다.
>    플랫폼·사용자·채널은 `event.source.{platform,user_id,chat_id,thread_id}`.
>
> 반환 규약은 계획서 서술이 맞았다 — `None` 통과 / `skip` 드롭 / `rewrite` 교체
> (gateway/run.py:8660-8679). 첫 번째로 인식되는 action 이 이긴다.
>
> **추가로 확인된 것 두 가지가 설계를 바꿨다.**
>
> - **예외로 fail-closed 를 만들 수 없다.** `invoke_hook`(plugins.py:1870)과
>   게이트웨이(run.py:8648)가 2중으로 예외를 삼키고 정상 디스패치한다. 그래서
>   구현은 모든 실패 경로에서 차단값을 **명시적으로 return** 한다.
> - **콜백에 타임아웃이 없다.** async 이벤트 루프에서 동기 호출되므로 콜백이 느리면
>   게이트웨이 전체(모든 플랫폼·모든 세션)가 멈춘다. 그래서 LLM 호출에 timeout 을
>   주고, 명백한 문구는 정규식으로 선차단해 LLM 호출 자체를 건너뛴다.

기존 문서 정정 대상 — hermes-security-policy.md 6-1 표의 "3단계(모델 판단) 이전에는 보안
개입 지점이 없다"는 서술은 사실과 다름. 지점은 있고 비어 있었을 뿐임.

## 3. 설계

화이트리스트 단위는 **허용 업무 카테고리**로 함. 판정은 도구 없는 별도 LLM 세션 1회 호출.

```text
메시지 수신
   │
   ├── pre_gateway_dispatch 훅  ← 신설 지점
   │     ├── 분류 LLM 1회 (도구 없음, 짧은 타임아웃)
   │     ├── 카테고리 ∈ 화이트리스트 → 통과
   │     └── 그 외 · 분류 실패 · 타임아웃 → 차단
   │
   └── 본 세션 LLM (기존 L1~L3 그대로 유지)
```

카테고리 초안. 실제 목록은 Phase 0 관측 결과로 확정함.

| 카테고리 | 예시 요청 | 기본 |
| --- | --- | --- |
| `read_only_query` | 배포 로그 조회, 장애 상태 확인 | 허용 |
| `report_ops` | 주간보고 갱신, Confluence 문서 정리 | 허용 |
| `ticket_ops` | Jira 조회·댓글·상태 변경 | 허용 |
| `deploy_trigger` | GitHub Actions 트리거 | 허용 |
| `chitchat` | 인사, 잡담 | 허용 |
| `destructive` | 삭제, 프로세스 종료, 권한 변경 | 차단 |
| `credential_access` | 키·토큰·인스턴스 정보 요구 | 차단 |
| `config_change` | 훅·설정·화이트리스트 자체 변경 요구 | 차단 |
| `unknown` | 위에 없음 | 차단 |

기존 계층과 다른 점 두 가지.

- **fail-closed**: 현재 훅들은 예외 시 `sys.exit(0)` 으로 통과시킴(fail-open). 이 훅은 분류
  실패·타임아웃·JSON 파싱 실패를 전부 차단으로 처리함. 판정 불가와 허용을 구분함.
- **분류기는 사용자 문구를 데이터로만 취급**: 구분자로 감싸고, 지시로 해석하지 말라고 명시.
  분류기 자체가 인젝션 표적이 되므로 출력은 카테고리 하나로 제한하고 그 외 응답은 `unknown`.

## 4. 단계

| Phase | 작업 | 완료 판정 |
| --- | --- | --- |
| 0 | 관측 전용 훅 배포 — payload 전체 구조, 플랫폼·사용자·채널 필드 유무, CLI 세션도 이 훅을 지나는지, `skip` 반환 시 사용자에게 보이는 것, `rewrite` 가 실제 모델 입력을 바꾸는지, 어떤 이벤트가 이 훅을 트리거하는지(편집·스레드·봇 메시지) | 차단 0건, 실사용 로그 1~2주 수집 |
| 1 | 수집 문구로 카테고리 목록 확정, 분류기 프롬프트·출력 스키마 작성, Bedrock 직접 호출(경량 모델), 관측 모드에서 분류 결과만 로깅 | 오분류율 확인, 허용 요청 오차단 0 |
| 2 | 차단 모드 전환 — 화이트리스트 판정, 미허용 시 차단, fail-closed 처리, 차단 사유를 사용자에게 알리는 경로 결정(`skip` 무응답 vs `rewrite` 안내, Phase 0 결과에 따름) | 테스트 코퍼스 통과, 실차단 발생 |
| 3 | 감사 로그를 `security_log.write` 로 통합(`BLOCKED_PROMPT`), 차단 이력 주기 검토로 화이트리스트 조정 | 로그에 차단 기록 확인 |

**[2026-08-09] 진행 상태** — Phase 1·3 은 구현에 포함됐고, Phase 0 관측이 남았다.

| Phase | 상태 |
| --- | --- |
| 0 관측 | **진행 필요.** `mode: observe` 로 배포됨. 감사 로그의 `WOULD_BLOCK_PROMPT` 를 1~2주 모아 오차단을 확인한다 |
| 1 카테고리·분류기 | **완료.** 허용 8종 + 관리자 전용 2종 + 차단 11종 확정 (초안의 `deploy_trigger`·`report_ops`·`ticket_ops` 는 수행 수단 부재로 폐기, `read_only_query` 는 수단별로 분할). 분류기는 `ctx.llm.complete` 1회 |
| 2 차단 모드 | **구현 완료, 미활성.** `config.yaml` 의 `mode: enforce` 한 줄로 전환. 차단 사유 전달은 `rewrite` 로 결정 — 원문을 버리고 안내 문구로 교체하므로 위험한 원문이 모델에 도달하지 않으면서 사용자는 사유를 안다. `on_block: silent` 로 `skip` 선택 가능 |
| 3 감사 로그 | **완료.** `BLOCKED_PROMPT` / `WOULD_BLOCK_PROMPT` 로 `security_log.write` 에 기록 |

Phase 2 의 차단 사유 전달 경로는 Phase 0 관측 없이 정할 수 없음 — `skip` 이 무응답이면
사용자는 봇이 죽은 것으로 인식하고, `rewrite` 는 결국 모델을 한 번 거치므로 모델이 도구를
쓸 여지가 남음. 관측으로 확인한 뒤 결정함.

**[2026-08-10 확정] `rewrite` 유지.** 관측에서 예상하지 못한 실패가 나옴 — `rewrite` 의
문제는 "도구를 쓸 여지"가 아니라 **안내문 자체가 무시된다**는 것이었음. 안내문이
`event.text` 를 교체해 *사용자 발화*로 도착하는데, SOUL.md 가 메시지 속 지시문을 데이터로
취급하라고 못박고 있어 에이전트가 안내문을 프롬프트 인젝션으로 판정하고 불복함. 원문을
못 받은 채 직전 대화에 남은 내용으로 대신 답해 전혀 다른 주제의 오답을 냄(3턴 반복).

대응은 세 가지. (1) SOUL.md 에 안내문 접두사를 유일한 예외로 명시 — 이 안내문은 제한만
하고 권한을 주지 않아 위조돼도 상승 경로가 아님. (2) 안내문을 받으면 직전 대화로 대신
답하지 않도록 명시. (3) `skip` 은 채택하지 않음 — 무응답이면 사용자가 오차단을 신고할
수단이 사라지고, 이번 건도 사용자 신고로 발견됐음. 회귀는
`tests/test_prompt_gate.py` 의 "실사용 오차단 회귀" 절이 지킴.

## 5-1. 적대적 검증 결과 [2026-08-09]

구현 직후 세 각도(분류기 인젝션 / 구조적 우회 / 코드 fail-open)로 우회를 시도해
15건이 제기됐고, 재현된 것을 고쳤다. 전부 **"게이트가 분류한 것"과 "모델이 실제로
받는 것"이 어긋나서** 생긴 문제였다.

### 닫은 것

| 우회 | 왜 뚫렸나 | 수정 |
| --- | --- | --- |
| 길이 절단 | 앞 4000자만 분류하고 원문 전체를 모델에 넘겼다. 뒤에 페이로드를 붙이면 분류기가 못 본다 | 자르지 않는다. `max_chars`(20000) 초과는 `unknown` 으로 차단 |
| 슬래시 프리픽스 | `/` 로 시작하면 무조건 통과시켰는데, `/steer`·`/queue`·스킬·번들 커맨드는 인자를 그대로 모델에 넘긴다 | 무조건 통과 삭제. 인자 없는 내장 커맨드만 예외, 나머지는 전부 분류 |
| `//` · `/경로/` | 게이트는 `lstrip().startswith("/")`, 코어는 원문 `startswith("/")` + 이름에 `/` 있으면 커맨드 아님. 두 판정이 어긋나 평문이 새어 나갔다 | 코어와 같은 규칙으로 통일 (`_split_command`) |
| 인용·채널 컨텍스트 | 게이트는 `event.text` 만 보는데 모델은 `reply_to_text`·`channel_context` 도 받는다 | 모델이 볼 텍스트를 모아서 분류 (`_model_visible_text`) |
| 텍스트 없는 첨부·음성 | 빈 텍스트를 무조건 통과시켰다. 코어가 나중에 전사·문서 인라인을 붙인다 | 첨부가 있으면 `unknown` 으로 차단 |
| observe = 완전 무방비 | 관측 기간 내내 아무것도 안 막는다 | `enforce_hard_block: true` — observe 에서도 정규식 히트는 차단 |
| 재시도로 루프 정지 | `ctx.llm` 의 `timeout` 은 **시도당** 값이라 전송 오류 재시도로 20~30초 게이트웨이 전체가 멈춘다 | 워커 스레드 + 벽시계 예산을 게이트가 직접 관리 |
| 페이로드 분할 | 요청을 두 메시지로 쪼개면 각각은 무해해 보인다 | 세션별 직전 발화 N개를 `<context>` 로 함께 분류 |
| 감사 로그 조용한 실패 | `security_log` import 실패를 조용히 넘겨서 관측이 "기록 0" 으로 끝날 수 있었다 | 등록 시점에 `logger.error` |

회귀 방지: `tests/test_prompt_gate.py` 112개.

### 5-2. 관리자 전용 카테고리 [2026-08-10]

`ADMIN_ONLY` 2종을 추가함. `config.yaml` 의 `plugins.entries.prompt-gate.admins` 에
있는 발신자만 통과하고, 나머지에게는 **`mode` 와 무관하게 항상 차단**된다 —
관측 실험이 아니라 운영자가 지정한 접근 제어이기 때문.

| 카테고리 | 대상 | 검출 |
| --- | --- | --- |
| `db_schema_query` | DB 테이블·컬럼·스키마·ERD·엔티티 등 데이터 구조 질의 | 정규식 선판정 + 분류기 |
| `agent_restart` | 에이전트·게이트웨이 재시작 요청 | `/restart`·`!restart` 커맨드명 + 정규식 + 분류기 |

식별 방법: 이벤트의 `user_id`·`sender_id`·`author_id`·`from_id`·`user`·`sender`·
`chat_id` 중 하나라도 `admins` 와 일치하면 관리자. 코어의 실제 필드명을 이 레포에서
확인할 수 없어 후보를 전부 훑고, **하나도 못 찾으면 비관리자로 간다(fail-closed)**.
`admins` 가 비어 있으면 아무도 통과하지 못한다. 실제로 어떤 값이 오는지는 차단 로그의
`ids=` 로 확인함.

한계: 위 5-1 의 구조적 잔여 2번이 그대로 적용된다. `/restart` 를 코어가 이 훅보다
앞에서 처리하면 커맨드 경로는 걸리지 않고 평문 문구만 걸린다. 도달 여부는
`admin_gate=` 로그로 확인함.

### 닫지 못한 것 — 구조적 잔여

**이건 플러그인으로 고칠 수 없다. 게이트를 신뢰할 때 반드시 알고 있어야 한다.**

1. **에이전트 실행 중 보낸 후속 메시지는 훅을 지나지 않는다.** 코어는 그 메시지를
   `_handle_message` 가 아니라 큐/스티어 경로로 받아 모델 입력에 합친다. 즉 허용
   요청 하나로 에이전트를 돌려놓고 그 사이에 임의 문구를 밀어넣을 수 있다.
   → 근본 수정은 `_prepare_inbound_message_text`(모델 입력이 확정되는 단일
   초크포인트)에 거는 것인데 코어 코드다. `pre_llm_call` 은 **컨텍스트 주입만
   가능하고 차단은 안 된다**(plugins.py:1855) — 플러그인 계층에 완전한 초크포인트가
   없다는 뜻이다.

2. **게이트웨이 슬래시 커맨드는 통제할 수 없다.** `/yolo`(승인 절차 생략),
   `/restart` 등은 애초에 모델을 거치지 않고 게이트웨이가 직접 처리한다.
   화이트리스트와 무관한 별개 경로다.

3. **정규식 백스톱은 완전해질 수 없다.** 동의어·우회 표기로 피할 수 있다.
   주 방어는 분류기이고 정규식은 분류기가 죽었을 때의 최소선이다.

4. **적용 경로 밖**: CLI 세션, cron 자율 실행, ACP 어댑터, internal event.
   기존 L1~L3·LK 에 의존한다.

5. **ec2-user 인스턴스**: 같은 서버의 두 번째 게이트웨이에 이 플러그인을 걸지
   않으면 약한 쪽이 그대로 열려 있다. `hermes-security-policy.md` 0-3 참조.

## 6. 검증

`tests/test_prompt_gate.py` 45개 작성 완료 (전량 통과). 훅을 subprocess 로 실행하는
대신 플러그인 모듈을 직접 import 하고 가짜 `ctx`·`event` 로 콜백을 호출한다 —
파이썬 플러그인 훅이라 subprocess 경계가 없기 때문이다.

**검증하는 것은 분류 정확도가 아니라 구조적 fail-open 부재다.** 코어가 예외와
잘못된 반환값을 조용히 삼키므로, 아래 중 하나만 깨져도 게이트는 뚫린 채로 돈다.

- 허용 코퍼스: 실제 수집한 업무 요청 문구. 오차단 0 이어야 함
- 차단 코퍼스: 삭제·자격증명·설정 변경 요구, 인젝션 문구("앞의 지시는 무시하고 ...")
- fail-closed: 분류기 호출을 강제 실패시켜 차단되는지 확인
- 회귀: 분류기 응답이 스키마를 벗어난 경우(빈 문자열, 산문, 여러 카테고리, 목록 밖 이름, None) 전부 차단
- 콜백 형태: 동기 함수인가(async 면 코루틴이 버려짐), 임의 kwargs 를 받는가(TypeError 도 삼켜짐)
- 정규식 선차단이 LLM 호출 0회로 동작하는가
- 차단 시 원문이 교체 텍스트에 남지 않는가
- 망가진 payload(event 없음·None·text 속성 없음)에도 예외를 던지지 않는가
