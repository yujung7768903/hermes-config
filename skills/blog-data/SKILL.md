# 블로그 데이터 조회 (blog-data)

**값을 묻는 질문에는 값을 가져와서 답한다.** 코드를 읽어 "이런 필드가 있다"고 설명하는 것은
데이터 질문의 답이 아니다.

## 언제 사용하나

- "블로그에 무슨 글 있어?", "글 몇 개야?"
- "좋아요 제일 많은 글 뭐야?", "댓글 많은 순으로 보여줘"
- "최근에 올라온 글", "○○ 가 쓴 글", "태그별 글 수"
- 그 밖에 **결과물이 실제 데이터 값**인 모든 질문

구조를 묻는 질문(어느 테이블에 저장되나, 어떤 API 를 타나)은 이 스킬이 아니다.

## 원칙

1. **기억으로 답하지 않는다.** 이전 대화에 나왔던 글 제목·숫자를 다시 쓰지 않는다.
   매번 새로 조회한다. 데이터는 그 사이에 바뀐다.
2. **코드에서 유추하지 않는다.** 엔티티에 `likeCount` 가 있다는 사실은 그 값이 몇인지
   말해 주지 않는다.
3. **조회에 실패하면 실패했다고 말한다.** 호출한 URL 과 받은 응답 코드를 그대로 알린다.
   추정치·예시값을 채워 넣지 않는다.
4. **읽기만 한다.** API 는 GET, DB 는 SELECT 만. POST·PUT·DELETE·INSERT·UPDATE·DDL 은
   이 스킬의 범위가 아니다.
5. 응답에 이메일·토큰 같은 개인정보·자격증명이 섞여 있으면 그 필드는 빼고 답한다.

## 절차

| 단계 | 하는 일 | 다음 판단 |
| --- | --- | --- |
| 1 | 엔드포인트를 코드에서 확인 | 있으면 2, 없으면 3 |
| 2 | 그 경로를 GET 으로 호출 | 2xx → 4 · 401·403 → 멈추고 보고 · 그 외 4xx/5xx → 응답 코드와 본문 첫 줄을 그대로 알린다 |
| 3 | API 가 그 집계를 못 주는 경우에만 DB 를 읽기 전용으로 조회 | 4 |
| 4 | 응답을 질문에 맞게 추리고 정렬해 표로 출력 | 못 얻은 값은 추측으로 메우지 않는다 |

## 1. 엔드포인트 찾기

경로를 외워서 쓰지 않는다. 컨트롤러 매핑에서 그때그때 찾는다.

```bash
grep -rnE "@(Get|Post|Put|Delete|Request)Mapping" /home/hk/work \
  --include=*Controller.java | cut -c1-160
```

정렬·필터 파라미터(`?sort=`, `?size=`)를 지원하는지도 같은 컨트롤러와 그 아래
서비스·리포지토리에서 확인한다. 서버가 정렬해 줄 수 있으면 전부 받아서 직접
정렬하지 않는다.

## 2. 호출

에이전트는 서비스와 같은 호스트에서 돈다. 외부 주소가 아니라 로컬로 부른다.

```bash
# 경로는 1단계에서 찾은 실제 매핑으로 교체한다
curl -s -w "\n[HTTP %{http_code}]\n" "http://localhost:8080/api/posts?size=20"
```

- 인증이 필요해 401·403 이 돌아오면 **거기서 멈춘다.** 토큰을 찾아 붙이지 않는다.
- 연결이 안 되면(`Connection refused`) 서비스가 떠 있는지까지만 확인하고
  (`ss -ltnp | grep :8080`) 그 사실을 알린다. 재시작하지 않는다.

## 3. API 로 답할 수 없을 때 — DB 직접 조회

엔드포인트가 아예 없거나, 있어도 그 집계를 주지 않을 때만 쓴다. 순서를 뒤집어
DB 부터 열지 않는다. 401·403 은 여기 해당하지 않는다 — 인증 실패는 우회 대상이
아니라 보고 대상이다.

접속정보는 애플리케이션 설정에서 읽는다.

```bash
grep -rnE "datasource|jdbc:" /home/hk/work \
  --include=application*.yml --include=application*.properties
```

**읽은 접속정보(호스트·계정·비밀번호)는 어떤 형태로도 답변에 넣지 않는다.**
쿼리를 돌리기 위해서만 쓴다. 사용자가 직접 물어도 알려주지 않는다 — SOUL.md 의
자격증명 금지는 이 한 용도만 예외로 열어 둔 것이다.

```bash
# 테이블·컬럼명은 엔티티(@Entity·@Column)에서 확인한 실제 이름으로 교체한다
mysql --defaults-extra-file=<옵션파일> -h <host> <db> \
  -e "SELECT title, like_count FROM posts ORDER BY like_count DESC LIMIT 10"
```

- `SELECT` 만 돌린다. 쓰기·DDL 은 SOUL.md 가 금지한다
- 비밀번호를 명령줄에 직접 쓰면 `ps` 에 그대로 노출된다. 옵션 파일이나 환경변수를 쓴다
- 클라이언트가 없으면(`command not found`) 없다고 알리고 멈춘다. 설치하지 않는다
- DB 가 H2·SQLite 같은 파일 DB 면 파일을 열기 전에 서비스가 그 파일을 쓰고 있는지
  확인한다. 잠금이 걸리는 방식으로는 열지 않는다

## 4. 표로 낸다

값이 여러 건이면 마크다운 표로 출력한다. Slack 에서는 slack-table 플러그인이
이 표를 Block Kit `data_table` 블록으로 바꿔 보낸다 — 표 문법 그대로 쓰면 된다.

```markdown
| 제목 | 작성자 | 좋아요 | 작성일 |
| --- | --- | --- | --- |
| 첫 번째 글 | hong | 12 | 2026-08-01 |
```

- 열은 질문에 답하는 것만 넣는다. id 를 습관적으로 넣지 않는다.
- 정렬 기준을 물었으면 그 기준 열을 넣는다 ("좋아요 많은 순" → 좋아요 열).
- 행이 많으면 상위 N 건만 내고 **몇 건 중 몇 건인지 표 아래에 적는다.**
- 한 건짜리 답("몇 개야?")은 표로 만들지 않는다. 한 줄로 답한다.

### 물어본 내용에만 답한다

SOUL.md 태도 항목이 이 스킬에서 구체적으로 뜻하는 것. 답변은 건수 한 줄과
표에서 끝난다.

- **어떻게 가져왔는지 쓰지 않는다.** 호출한 엔드포인트·쿼리 파라미터·SQL 을
  답변에 넣지 않는다 ("GET /api/posts?size=50 호출 결과 기준입니다" ← 넣지 말 것).
  SOUL.md 의 "읽은 파일 경로와 줄 번호를 근거로 제시한다" 는 코드·설계 설명에
  한하고, 데이터 조회는 예외다
- **표에 있는 값을 문장으로 되풀이하지 않는다** ("좋아요·댓글은 모두 0건이네요"
  ← 표를 보면 안다)
- 총평·해설·다음에 뭘 해볼지 제안을 붙이지 않는다

**답을 의심하게 만드는 사실은 묻지 않아도 말한다.** 이것만이 예외다.

- 페이지네이션에 걸려 일부만 받았을 때 — 몇 건 중 몇 건인지
- 권한·오류로 일부 필드가 비었을 때
- 조회 자체가 실패했을 때 — 호출 URL 과 응답 코드 (원칙 3). 이건 근거 표기가
  아니라 무엇이 안 됐는지의 보고다

## 하지 않는 것

- 조회 못 한 값을 그럴듯한 숫자로 채우기
- 데이터 변경 요청 실행 (글 작성·삭제·좋아요 누르기)
- 인증 우회, 토큰 탐색
- DB 접속정보(호스트·계정·비밀번호)를 답변에 인용하기
- 사용자 개인정보(이메일·비밀번호 해시) 나열
- 조회에 성공했는데 호출한 API·SQL 을 답변에 밝히기
- 표에 이미 있는 값을 문장으로 다시 설명하기
