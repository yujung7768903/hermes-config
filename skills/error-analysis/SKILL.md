# 에러·장애 원인 분석 (error-analysis)

증상만 있는 문의에 **로그를 먼저 읽고** 답한다. 코드는 로그에서 나온 사실을 설명할 때 읽는다.

## 언제 사용하나

- "블로그 글 작성이 안 돼", "버튼 눌러도 반응이 없어", "에러가 나", "느려" 처럼 증상만 있는 문의
- 사용자가 에러 메시지·스택트레이스를 주지 않은 경우 (기본값으로 이렇게 온다)
- 특정 기능이 특정 시각에 실패했다는 신고

## 원칙

1. **스택트레이스를 사용자에게 요구하지 않는다.** 직접 읽는다. 사용자에게 무엇을 브라우저에서 확인해 달라고 시키는 것은 로그를 다 뒤진 뒤 마지막 수단이다.
2. 되묻는 것은 **증상과 재현 조건**까지다 — 언제, 어느 화면, 어떤 동작. 이건 로그 검색 범위를 좁히는 데 쓴다. 답을 기다리지 말고 그 사이에 로그를 읽는다.
3. **로그 사실 → 판단 → 코드 근거** 순서로 답한다. 코드만 읽고 "원인을 찾았다"고 말하지 않는다. 로그 확인이 없으면 그건 원인이 아니라 가능성이다.
4. 못 읽은 로그는 **못 읽었다고 말한다.** 경로와 사유(없음·권한 없음)를 그대로 알린다. 우회하지 않는다.
5. 로그·프로세스 출력에 자격증명이 섞여 있으면 사용자에게 전달하지 않는다. 인용은 경로·시각·에러 메시지·스택트레이스로 한정한다.

## 절차

| 단계 | 하는 일 | 다음 판단 |
| --- | --- | --- |
| 0 | 시각 확정 — 문의 메시지 시각 기준 ±10분을 검색 창으로 잡는다 | |
| 1 | 로그 위치 찾기 (아래 명령) | 못 찾으면 그 사실을 보고하고 원칙 4 |
| 2 | 해당 시각에 **요청이 서버에 도달했는지** 확인 | 도달 O → 3, 도달 X → 4 |
| 3 | 예외·스택트레이스·응답 코드 확인 → 그 지점 코드와 대조 | 원인 지목 |
| 4 | nginx·정적 자산 로그 확인. 여기도 조용하면 프론트 구간 | 5 |
| 5 | 프론트 구간이면 "요청이 서버까지 오지 않았다"까지만 사실로 말하고, 코드 가설은 가설로 표시한다 | |

## 로그 위치 찾기

경로를 외워서 쓰지 않는다. 그때그때 찾는다.

```bash
# 1. 떠 있는 프로세스와 포트
pgrep -af "java|node|ng serve|nginx" | cut -c1-120
ss -ltnp 2>/dev/null | grep -E ":8080|:4200|:80"

# 2. 그 프로세스가 열고 있는 로그 파일 (PID 는 위에서 확인)
ls -l /proc/<PID>/fd 2>/dev/null | grep -E "\.log|\.out"

# 3. systemd 로 떠 있으면
systemctl list-units --type=service --no-pager | grep -Ei "blog|spring|api|front|nginx"
journalctl -u <unit> --since "-30min" --no-pager | tail -300

# 4. 파일 로그 후보
ls -lt /home/hk/work/**/*.log /home/hk/work/*.log /var/log/nginx/*.log 2>/dev/null | head -20
```

`Permission denied` 가 나면 그 경로를 사용자에게 그대로 알린다. 권한 획득을 시도하지 않는다.

## 증상별 첫 확인 대상

| 증상 | 먼저 볼 로그 | 무엇을 찾나 |
| --- | --- | --- |
| 버튼 눌러도 반응 없음 | 백엔드 app/access 로그 | 그 시각에 해당 POST/PUT 요청이 **있었는지** |
| 에러 화면 · 5xx | 백엔드 app 로그 | 스택트레이스 최상단 예외와 클래스·줄 |
| 저장은 됐는데 화면에 없음 | 백엔드 access 로그 | 200 인데 응답이 빈 값인지, 후속 GET 이 왔는지 |
| 로그인 풀림 · 401 · 403 | 백엔드 security 로그 | 인증 실패 사유, 토큰 만료 시각 |
| 느림 · 타임아웃 | 백엔드 access 응답시간, DB 로그 | 느린 요청의 엔드포인트와 소요시간 |
| 화면이 아예 안 뜸 | nginx access/error | 정적 자산 4xx, upstream 연결 실패 |

## 요청 도달 여부 확인 예

엔드포인트를 코드에서 먼저 확인하고(컨트롤러 매핑), 그 경로로 로그를 검색한다.

```bash
# 시각 + 엔드포인트로 좁힌다. 로그 파일 경로는 위에서 찾은 값으로 교체
grep -nE "POST +/api/posts" <로그경로> | tail -40
# 프레임워크가 access 로그를 안 남기면 예외만이라도
grep -nE "Exception|ERROR|WARN" <로그경로> | tail -60
```

**없다는 것을 근거로 쓰기 전에, 그 로그가 요청을 기록하는 로그인지 먼저 확인한다.**
Spring Boot 는 기본값으로 HTTP access 로그를 남기지 않는다 — 그런 로그에서 요청이
안 보이는 것은 "요청이 없었다" 가 아니라 "이 로그로는 알 수 없다" 다.

```bash
# access 로그가 켜져 있나
grep -rnE "accesslog|access_log|logging.level" /home/hk/work --include=application*.properties --include=application*.yml 2>/dev/null
# 같은 시간대에 다른 정상 요청이 이 로그에 찍혀 있나 (기록되는 로그인지의 실측)
grep -cE "GET|POST" <로그경로>
```

기록되는 로그임이 확인된 뒤에야 "그 시각에 이 엔드포인트로 들어온 요청이 로그에 없다" 를
사실로 쓸 수 있고, 그건 프론트에서 요청이 나가지 않았다는 뜻이다. 이때 흔한 원인은 클라이언트 측 조기 리턴(입력 검증), 예외로 인한 핸들러 중단, 에러 무시(subscribe 에러 핸들러 없음)다 — 코드에서 확인해 **가능성**으로 제시한다.

## 하지 않는 것

- 로그 확인 전에 원인 단정
- 재시작·설정 변경·프로세스 종료 (읽기만 한다)
- 사용자에게 F12·Network 탭 확인을 먼저 시키는 것 — 서버에서 확인할 수 있는 것을 다 본 뒤에만 요청한다
